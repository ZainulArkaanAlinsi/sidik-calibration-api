# Audit bug — 2 Sep 2026

Hasil menjalankan *Prompt Pack Audit Bug* (Recon → Bug Hunt) pada dua repo:
`sidik-calibration-api` dan `sidik-calibration-mobile`.

**Belum ada satu baris kode produksi yang diubah.** Berkas ini daftar temuan, sesuai
aturan Prompt 2 ("jangan tulis perbaikan dulu"). Perbaikan dikerjakan satu per satu
lewat Prompt 3, dengan urutan yang diusulkan di bagian terakhir.

## 1. Konteks yang dipakai

Blok konteks di prompt pack-nya kosong, jadi diisi dari repo — bukan dari ingatan.

| | |
|---|---|
| **API** | Laravel 13.19.0 · PHP 8.4 (constraint `^8.3`) · Filament 5.6.8 · Sanctum 4.3.2 · dompdf 3.1.2 · Reverb 1.11.1 · MySQL 8 · PHPUnit 12.5.31 |
| **Mobile** | Flutter ≥ 3.44.0 (CI pin 3.44.6) · Dart ≥ 3.12 · **Riverpod 3**.3.2 · http 1.6 · ML Kit teks 0.15 / barcode 0.14 · Firebase Messaging 16.5 |
| **Ukuran** | API 312 berkas PHP / 216 berkas test · Mobile 252 berkas Dart / 174 berkas test |
| **Lingkungan audit** | Container tanpa MySQL dan tanpa Flutter SDK. Test PHP dijalankan di SQLite in-memory (sama dengan `phpunit.xml` dan CI). Test Flutter **tidak bisa** dijalankan di sini |

### Alur data, singkatnya

Teknisi login (token Sanctum) → pilih alat pelanggan → server mengirim **bentuk lembar
kerja** sesuai profil alat (24 profil terdaftar di `CalibrationProfileRegistry`) →
teknisi mengisi titik ukur, manual atau lewat OCR on-device → `POST /calibrations` →
`CalibrationValidator` + kalkulator per-alat + `GumCalculator` menghitung budget
ketidakpastian dan vonis PASS/FAIL → admin approve → `GenerateCertificate` merakit
snapshot beku + PDF + QR → sertifikat → berkas masuk Folder Manager → publik bisa
memverifikasi lewat `GET /verify/{qr_token}`.

### Sifat yang menentukan seluruh audit ini

Proyek ini **tidak punya global scope**. Tidak ada trait, tidak ada `addGlobalScope`,
tidak ada middleware penyaring. 315 saringan `organization_id` ditulis tangan. Database
produksi masih **satu organisasi**, jadi query yang lupa disaring mengembalikan hasil
yang persis sama dengan query yang benar — lolos test, lolos Postman, lolos lapangan,
sampai lab kedua di-onboard.

Konsekuensi buat metode audit: lubang kelas ini **tidak bisa ditemukan dengan mencoba**.
Cuma dua hal yang menangkapnya — membaca query-nya, dan test yang sengaja membuat dua
organisasi.

### Catatan kejujuran soal premis prompt pack-nya

Prompt pack ini menyuruh "asumsikan ada masalah yang kelihatan benar tapi sebenarnya
salah" karena kodenya digenerate AI. Untuk repo ini asumsi itu **sebagian besar tidak
berlaku**, dan memaksakannya justru menghasilkan temuan palsu. Yang ditemukan bukan
kode yang asal jadi, tapi: komentar WHY yang panjang dan bertanggal, penjaga pembagi-nol
yang konsisten, 216 berkas test dengan penjaga lantai pada sapuan berbasis registry, dan
insiden nyata yang sudah didokumentasikan sendiri.

Jadi aturan yang dipakai: **keputusan yang sudah dijelaskan sadar di komentar bukan bug.**
Beberapa kandidat digugurkan karena aturan ini. Yang tersisa di bawah adalah celah yang
lolos dari pola pengamanan yang sudah konsisten di tempat lain — hampir semuanya
dibuktikan dengan menunjuk saudara sekelasnya yang sudah benar.

### BUG-001 · P1 · Jatah rate limit berbagi satu ember per user

- **Kategori** F (race/state) + D (environment)
- **Lokasi** `routes/api.php` + `routes/web.php` — 16 rute ber-`throttle:N,1`
- **Status** ✅ **SUDAH DIPERBAIKI** — dijaga `tests/Feature/JatahThrottleTerpisahPerEndpointTest.php`

Sumber Laravel 13.19.0 yang benar-benar terpasang,
`vendor/laravel/framework/src/Illuminate/Routing/Middleware/ThrottleRequests.php:224`:

```php
protected function resolveRequestSignature($request)
{
    if ($user = $request->user()) {
        return $this->formatIdentifier($user->getAuthIdentifier());  // route TIDAK ikut
    } elseif ($route = $request->route()) {
        return $this->formatIdentifier($route->getDomain().'|'.$request->ip());
    }
```

dan baris 98: `'key' => $prefix.$this->resolveRequestSignature($request)`, dengan
`$prefix` bawaan `''` — tidak ada satu rute pun yang mengisi argumen ketiga.

Artinya untuk request yang **sudah login**, kuncinya cuma id user. Ke-12 rute itu
menabung ke counter yang sama, sementara batasnya beda-beda:

| Rute | Jatah |
|---|---|
| `/worksheet-scans/{scan}/sel/{kunci}/crop` | 300/mnt — dipanggil **sekali per sel** |
| `/calibrations/preview`, `/calibrations/autoclave/preview` | 120/mnt |
| `/dokumen/bacaan/{id}`, `/dokumen/bacaan/{id}/koreksi` | 120/mnt |
| `/worksheet-scans` | 60/mnt |
| `/dokumen/baca`, `/raw-measurements/extract-from-photo` | 30/mnt |
| `/laporan/kalibrasi/export` | 20/mnt |
| `/certificates/{id}/kirim-email`, `/certificates/{id}/catat-whatsapp` | 20/mnt |
| `/audit-logs/export` | 20/mnt |

**Cara reproduksi** — login sebagai admin, panggil `POST /api/calibrations/preview`
21× (body boleh kosong; throttle jalan sebelum validasi), lalu panggil
`GET /api/audit-logs/export` satu kali. Hasil: **429**, padahal endpoint itu belum
pernah disentuh.

**Dampak nyata** — teknisi memindai satu lembar kerja (puluhan sel → puluhan panggilan
`crop`) langsung mengunci `extract-from-photo` dan seluruh endpoint 20/menit selama
sisa menit itu. Yang muncul di HP: *"Kebanyakan percobaan. Tunggu sebentar terus coba
lagi."* (`sidik-calibration-mobile/lib/services/api_client.dart:419`) — untuk tombol
yang belum pernah dia tekan. Pesannya secara harfiah salah menerangkan sebabnya.

**Kenapa ini lolos** — cacat yang sama persis **sudah disadari dan ditambal untuk jalur
tanpa login**. `app/Providers/AppServiceProvider.php:178` menjelaskannya sendiri:

> "buat request tanpa login, Laravel bikin kuncinya dari sha1(domain|ip) — nama
> route-nya nggak ikut."

Perbaikannya (limiter bernama untuk `login`/`register`/`password-reset`) berhenti di
cabang tamu. Cabang `$request->user()` — yang persis sama bentuknya — tidak pernah ikut
dipertimbangkan, dan `tests/Feature/RateLimitTest.php` cuma menguji dua limiter publik itu.

**Waktu diperbaiki, ternyata cabang tamunya pun belum bersih.** Empat rute publik masih
memakai limiter angka dan berbagi satu ember per IP: halaman verifikasi QR (30/menit),
tombol unduhnya (10/menit), versi aplikasi (60), dan verifikasi JSON (30). Akibatnya
pelanggan yang membuka halaman sertifikatnya sebelas kali menemukan tombol unduhnya mati
tanpa pernah menekannya. Itu direproduksi juga
(`test_jatah_unduh_verifikasi_tidak_ikut_habis_gara_gara_halaman_verifikasi`) dan ikut
diperbaiki — mekanismenya sama persis, jadi memperbaiki separuhnya berarti meninggalkan
cacat yang identik di permukaan yang justru dilihat orang luar.

### Perbaikannya

Enam belas limiter bernama didaftarkan di `AppServiceProvider::rateLimiters()`, mengikuti
pola yang sudah ada. **Nol angka jatah yang diubah** — yang diperbaiki cuma embernya.

Jalur yang sudah login dikunci per **orang**, bukan per IP:

```php
->by($nama.'|'.($request->user()?->getAuthIdentifier() ?? $request->ip()))
```

Sepuluh teknisi satu lab keluar lewat satu alamat IP. Kunci per-IP di jalur yang sudah
login berarti teknisi pertama yang sibuk mengunci sembilan temannya — dijaga
`test_dua_admin_punya_jatah_masing_masing`, yang merah kalau ada yang menyalin helper
per-IP yang lama ke sini.

Dua halaman web publik sengaja **tanpa** `->response()` JSON: yang membukanya browser,
bukan aplikasi kita, jadi Laravel merendernya sebagai halaman 429 biasa — persis
perilaku sebelumnya.

### BUG-002 · P1 · `resolusi = 0` lolos validasi dan diam-diam jadi 4 desimal di sertifikat

- **Kategori** B (validasi input)
- **Lokasi** `app/Http/Requests/EquipmentRequest.php:81`
- **Status** ✅ **SUDAH DIPERBAIKI** — dijaga `tests/Feature/ResolusiNolDitolakTest.php`

Dua baris di berkas yang sama, terpaut 22 baris:

```php
// baris 81 — kolom resolusi utama alat
'resolusi' => ['nullable', 'numeric', 'min:0'],

// baris 100-103 — saudaranya, sudah diperbaiki, komentarnya menjelaskan bug ini
// `min:0` nggak cukup: resolusi 0 bikin `desimalDariResolusi()` jatuh ke default 4 desimal
// diam-diam, dan sertifikatnya ngaku presisi yang alatnya nggak punya.
'resolusi_rentang.*.resolusi' => ['required', 'numeric', 'gt:0'],
```

`min:0` **mengizinkan angka 0**. Dan `app/Support/Angka.php:25` memperlakukan 0 persis
seperti null:

```php
if ($resolusi === null || $resolusi <= 0) {
    return self::DESIMAL_DEFAULT;   // = 4
}
```

**Dampak nyata** — untuk profil yang tidak meng-override `desimalSertifikat()` (pH Meter,
Turbidimeter, Chlorine, Conductivity, DO Meter, Centrifuge, Tachometer), kolom Standard
Value / UUT / Correction / U95% tercetak 4 desimal. Untuk alat beresolusi 0,1 itu persis
"presisi yang alatnya nggak punya" — kalimat yang ditulis sendiri di berkas itu, 22 baris
di bawah baris yang bocor.

**Cek apakah sudah terlanjur kena:**
```sql
SELECT id, nama_alat, resolusi FROM equipments WHERE resolusi = 0;
```

#### Dua pintu lain yang ditemukan sambil memperbaiki

`gt:0` di `EquipmentRequest` menutup jalur API. Dua jalur lain waktu itu masih terbuka,
dicatat terpisah karena **akibatnya berbeda**. Dua-duanya sudah ikut ditambal sesudahnya.

### BUG-024 · P1 · `resolusi_alat = 0` menghapus komponen resolusi dari budget Autoklaf

- **Kategori** B (validasi) → akibatnya E (angka)
- **Lokasi** `AutoclaveCalculationRequest.php:43,60` · `AutoclaveStoreRequest.php:84,99`
- **Status** ✅ **SUDAH DIPERBAIKI** — dijaga `tests/Feature/ResolusiAlatAutoklafNolDitolakTest.php`

Empat aturan dengan pola yang sama persis dengan BUG-002:

```php
'suhu.resolusi_alat'    => ['sometimes', 'nullable', 'numeric', 'min:0'],
'tekanan.resolusi_alat' => ['sometimes', 'nullable', 'numeric', 'min:0'],
```

Tapi akibatnya BUKAN empat desimal. Nilai itu mengalir lewat `AutoclaveInputBuilder`
ke `EnclosureCalculator`, dan di sana dia jadi komponen budget:

```php
'u' => ($resolusiAlat / 2.0) / $sqrt3,   // EnclosureCalculator:566
```

`resolusiAlat = 0` bikin `u` komponen itu **nol** — komponen daya-baca alat hilang dari
budget, dan **U95 yang tercetak lebih kecil dari yang seharusnya**. Sertifikat yang
mengklaim ketidakpastian lebih baik daripada yang alatnya sanggup.

`AutoclaveInputBuilder` memakai `?? $config['resolusi_alat']['suhu']`, dan `??` cuma
menangkap `null` — angka nol yang dikirim eksplisit lewat begitu saja.

#### Yang mengubah keputusannya

Waktu ini ditulis, saya menahannya karena mengira menambal berarti mengubah angka di
dokumen terakreditasi. **Itu keliru, dan perlu diluruskan:** perbaikan validasi cuma
menutup pintu buat sesi BARU. Dia tidak menghitung ulang apa pun dan tidak menyentuh satu
pun sertifikat yang sudah terbit. Yang benar-benar butuh keputusan cuma bagian keduanya —
apakah sesi lama perlu dihitung ulang — dan itu tetap terbuka.

Pertanyaan "apakah nol pernah sah" juga sudah terjawab dari kode, bukan dari tebakan.
`config/autoclave.php` menyimpan cadangan dari master (`INPUT DATA E16 / H16`): suhu
0,01 °C dan tekanan 0,001, dua-duanya positif. Komentarnya menyebut cadangan itu dipakai
"kalau teknisi nggak ngisi" — kasus `null`, yang ditangani `??` di `AutoclaveInputBuilder`.
Jadi nol eksplisit bukan "belum diisi" dan bukan resolusi nyata.

Akibatnya juga tidak lagi berupa dugaan: `test_nol_bikin_u95_lebih_kecil_dari_resolusi_master`
menghitung dua kali lewat `AutoclaveInputBuilder` + `AutoclaveCalculator` — sekali dengan
resolusi master, sekali dengan nol — dan membuktikan U95-nya memang mengecil. Test itu
menembus lapisan validasi dengan sengaja, supaya akibatnya tetap bisa ditunjukkan sesudah
pintunya ditutup.

**Yang MASIH terbuka:** apakah ada sesi tersimpan yang U95-nya terlanjur dihitung tanpa
komponen daya-baca. Itu butuh query ke database produksi, dan perbaikan ini tidak
menjawabnya:
```sql
SELECT id, nomor_sesi, JSON_EXTRACT(spesifikasi_alat, '$.suhu.resolusi_alat')
FROM calibration_sessions
WHERE JSON_EXTRACT(spesifikasi_alat, '$.suhu.resolusi_alat') = 0;
```

### BUG-025 · P2 · Impor Excel menulis `resolusi = 0` tanpa lewat validasi sama sekali

- **Kategori** B (validasi)
- **Lokasi** `app/Services/ExcelImporter.php:351` + `:356`
- **Status** ✅ **SUDAH DIPERBAIKI** — dijaga `tests/Feature/ImporResolusiNolDilewatiTest.php`

`POST /api/imports/excel` tidak melewati `EquipmentRequest`, jadi `gt:0` yang baru tidak
menjangkaunya:

```php
'resolusi' => $this->angka($nilai['resolusi'] ?? null),   // 0 → 0.0
...
], fn ($v): bool => filled($v));                          // filled(0.0) === true
```

`filled()` di Laravel cuma menganggap kosong itu `null`, string kosong, dan array kosong —
**angka nol lolos**. Jadi sel Excel berisi `0` mendarat sebagai `resolusi = 0.0`, dan
sertifikatnya kembali mencetak empat desimal.

#### Pertanyaannya ternyata sudah dijawab berkas itu sendiri

Waktu temuan ini ditulis saya menyimpannya sebagai keputusan pemilik proses: **tolak seluruh
barisnya**, atau **impor tanpa resolusi sambil melapor**? Yang pertama bisa memblokir impor
massal gara-gara satu sel; yang kedua diam-diam mengubah data lab.

Ternyata `ExcelImporter` sudah punya presedennya, dua puluh baris di atas tempat bug-nya,
untuk masalah yang persis sekelas:

> *"Nebak kategori dari nama alat gampang meleset dan hasilnya ketidakpastian yang salah di
> sertifikat — mending dilewati & dibenerin filenya."*

Penalarannya identik: nilai yang menghasilkan angka salah di sertifikat dikembalikan ke
pemilik berkas, bukan ditebak. Jadi ini bukan kebijakan baru yang saya karang — ini pola yang
sudah dipakai berkas itu, diterapkan ke satu kolom lagi.

Dan yang bikin "dilewati" aman: mode `uji_coba` menampilkan baris terlewat berikut alasannya
**sebelum** ada yang ditulis. Barisnya tidak hilang diam-diam; dia dikembalikan dengan
keterangan yang bisa dibaca. Dijaga
`test_uji_coba_sudah_menunjukkan_barisnya_sebelum_apa_pun_ditulis`.

Sel **kosong** tetap sah dan tetap diimpor — yang belum diketahui itu `null`, bukan nol.
Berkas lab lama banyak yang kolom resolusinya memang belum terisi, dan itu tidak boleh ikut
terblokir.

### BUG-022 · P3 · Fallback string `titik_ukur` tidak pernah jalan

- **Kategori** E
- **Lokasi** `sidik-calibration-mobile/lib/models/calibration_detail.dart:168-176`
- **Status bukti** [TERLIHAT DI KODE]; **diturunkan dari P0** setelah diperiksa

```dart
// Backend ngirim decimal(20,8) — bisa nyampe sebagai angka atau string.
titikUkur: (json['titik_ukur'] as num?)?.toDouble()
    ?? double.tryParse('${json['titik_ukur']}')
    ?? 0,
```

Di Dart, `x as num?` hanya lolos untuk `null` atau `num`. Kalau nilainya `String` — persis
kasus yang disebut komentarnya sendiri — ekspresi itu **melempar `TypeError` saat itu
juga**, jadi baris `?? double.tryParse(...)` tidak pernah tercapai. Perlindungan yang
tertulis di komentar tidak ada di kodenya.

**Kenapa P3, bukan P0:** `App\Models\RawMeasurement::casts()` di backend meng-cast
`titik_ukur` ke `'float'` (baris 23), jadi JSON-nya selalu angka. Jalur normal aman dan
kasus String tidak terjangkau hari ini. Yang tersisa: satu baris fallback yang mati, dan
komentar yang menjanjikan sesuatu yang tidak dilakukan kodenya.

Kalau suatu saat benar terjadi, akibatnya tidak kelihatan: exception-nya ditelan
`parse_list.dart:24` (`catch (_)`), barisnya hilang dari daftar tanpa jejak, dan penjaga
`kebuang` di `lembar_kerja_screen.dart:446` — yang justru dibangun supaya "angka yang
nggak ketemu barisnya HARUS diomongin" — beroperasi sesudah parsing, jadi tidak pernah
melihatnya.
